## Secrets to add before applying

Phases 3 and 4 declare three new variables. Terraform reads them from
`~/Documents/home-docker/tf/secrets.auto.tfvars`, which is gitignored (`tf/*.auto.tfvars`)
and exists only on the machine holding the state. Nothing here can be generated by an
apply; a human writes all three. Without them `tofu plan` stops and prompts for input
rather than failing, which is easy to mistake for a hang.

Append to `tf/secrets.auto.tfvars`, matching the `name = "value"` style already in
that file:

```hcl
restic_password               = "<generated, see below>"
alertmanager_telegram_token   = "<bot token from @BotFather>"
alertmanager_telegram_chat_id = "<numeric chat id>"
```

### `restic_password`

The encryption passphrase for the repository at `/mnt/backups/restic`. Generate it,
do not invent it:

```bash
openssl rand -base64 32
```

**There is no recovery path.** restic derives the repository key from this
passphrase; lose it and every snapshot is permanently unreadable, with no support
channel and no reset. Two consequences:

- Put it in a password manager **before** the first `tofu apply`, not after. The
  first apply creates the repository, and from that moment the passphrase is the only
  thing standing between you and total backup loss.
- It is not recoverable from the running container either. The value lives in the
  container's environment, so `docker inspect restic-data` shows it while the
  container exists, but that is a copy, not a backup, and it vanishes with the
  container.

Do not reuse an existing password here. This one protects the thing you restore from
when everything else is gone.

### `alertmanager_telegram_token` and `alertmanager_telegram_chat_id`

Both already exist. Target the same `@kcfam_bot` and chat that home-docker's Uptime
Kuma and gtfs.zone's Gatus use, so kcfam.us and gtfs.zone page one place. The gtfs
copies are in the `gtfs-app-secrets` Kubernetes Secret as `TELEGRAM_BOT_TOKEN` and
`TELEGRAM_CHAT_ID`, and can be read out with:

```bash
ssh kcfam 'export KUBECONFIG=/etc/rancher/k3s/k3s.yaml; \
  kubectl -n gtfs get secret gtfs-app-secrets \
    -o jsonpath="{.data.TELEGRAM_BOT_TOKEN}" | base64 -d; echo'
ssh kcfam 'export KUBECONFIG=/etc/rancher/k3s/k3s.yaml; \
  kubectl -n gtfs get secret gtfs-app-secrets \
    -o jsonpath="{.data.TELEGRAM_CHAT_ID}" | base64 -d; echo'
```

The chat id is declared `type = string` but is interpolated into the Alertmanager
config unquoted, because Alertmanager wants a YAML integer there. So write digits
only (a leading `-` is fine for a group chat); anything else renders an invalid
config and Alertmanager will not start.

### Where these end up

Neither Alertmanager secret is baked into an image. Both reach the container as
`upload` blocks at create time, so they exist in the Terraform state and in the
running container, and nowhere else. Treat `tf/terraform.tfstate` as secret material;
it is already gitignored.

## What happened

`/srv` (838G, `/dev/sda5`) is shared by Docker and Longhorn. It hit 100%.

Pruning images and containers reclaimed 78G but missed the cause. `du` accounted for
only 235G of the 754G in use:

| Path | Size |
|---|---|
| `/srv/docker` | 232.7G (192G of it `nextcloud_nextcloud`, real data) |
| `/srv/longhorn` | 2.9G |
| `/srv/lost+found` | empty |

The missing ~556G was three **deleted-but-still-open** tarballs held by the
`offen/docker-volume-backup` containers:

```
199.7G  backup-weekly  /tmp/homeserver-backup-20260906-030000.tar.gz (deleted)
196.8G  backup-daily   /tmp/homeserver-backup-20260812-020000.tar.gz (deleted)
159.5G  backup-daily   /tmp/homeserver-backup-20260907-020000.tar.gz (deleted)
```

offen stages its ~188G archive in the container's `/tmp`, which lands on `/srv` via
the container writable layer. On failure it unlinks the file but keeps the file
descriptor open, so the inode survives for the life of the container. `du` cannot see
that space and no prune can reclaim it.

The 2026-08-12 leak sat there for four weeks and ate the headroom. The Sep 6 weekly
and Sep 7 daily runs then hit the wall:

```
20260906-030000  archive/tar: write too long        (nextcloud.log, 133M, grew mid-tar)
20260907-020000  no space left on device
```

Because Longhorn's disk is the same filesystem, this took the k3s stack down with it:
`srv-disk` went `DiskPressure`, the `postgres` and `redis` replicas faulted, and
`postgres-1` and `gtfs-api` went CrashLoopBackOff.

Nothing surfaced any of it for four weeks. node-exporter and Prometheus scrape the
host, but `prometheus/prometheus.yml` has `rule_files` commented out and there is no
Alertmanager.

## Phase 1: recover the k3s cluster (done 2026-09-07)

**Outcome:** auto-salvage fired on its own once DiskPressure cleared; the manual
`failedAt` patches below were not needed. Both volumes came back `attached`/`healthy`
with data intact (`feed` 6 rows, `tracker` 5 rows, `gtfs_trip` 3033 rows). `postgres-1`
and `redis` recreated themselves, `gtfs-api` was restarted and stopped crashlooping,
CNPG reports `Cluster in healthy state`. `status.gtfs.zone` and `rt.gtfs.zone/health`
both 200.

The orphan PV under *Orphan to clean up* was deleted. Its backing
`volumes.longhorn.io/pvc-45d72ac9-...` survives the delete (reclaim policy `Retain`)
and is still listed as `detached`/`unknown`; deleting that object is the last 99M and
is optional.

Longhorn's `auto-salvage` setting is on by default and should fire once `srv-disk`
leaves DiskPressure. The threshold is 25% of 838G, so about 210G free is required;
Phase 0 gives ~646G.

Check before intervening:

```bash
ssh kcfam 'export KUBECONFIG=/etc/rancher/k3s/k3s.yaml; \
  kubectl -n longhorn-system get volumes.longhorn.io \
    -o custom-columns=NAME:.metadata.name,STATE:.status.state,ROBUSTNESS:.status.robustness'
```

If the two faulted volumes do not recover on their own, salvage them by hand. Note
that this Longhorn version's Volume CRD has **no** `spec.salvageRequested` field
(verified against the live CRD). Salvage works by clearing `failedAt` on the replica,
which is exactly what auto-salvage does internally:

```bash
ssh kcfam 'export KUBECONFIG=/etc/rancher/k3s/k3s.yaml; \
  kubectl -n longhorn-system patch replicas.longhorn.io \
    pvc-e2f6b26e-12a6-4184-9f98-39f42544339d-r-05a0b0e2 \
    --type=merge -p "{\"spec\":{\"failedAt\":\"\"}}"'

ssh kcfam 'export KUBECONFIG=/etc/rancher/k3s/k3s.yaml; \
  kubectl -n longhorn-system patch replicas.longhorn.io \
    pvc-5e4caeaa-f789-4c89-84fa-7c7b14e625de-r-7f70ba17 \
    --type=merge -p "{\"spec\":{\"failedAt\":\"\"}}"'
```

`pvc-e2f6b26e` is postgres (10Gi), `pvc-5e4caeaa` is redis (2Gi). Replica names are
from 2026-09-07 and may differ; re-read them with
`kubectl -n longhorn-system get replicas.longhorn.io`.

**There are no backups of either volume.** Salvage is the only recovery path. If a
replica cannot be salvaged, the data is gone and Postgres has to be rebuilt from the
GTFS source feeds. Say so out loud before doing anything destructive.

Once the volumes attach, restart the two crashlooping workloads:

```bash
ssh kcfam 'export KUBECONFIG=/etc/rancher/k3s/k3s.yaml; \
  kubectl -n gtfs delete pod postgres-1; \
  kubectl -n gtfs rollout restart deploy/gtfs-api'
```

`gtfs-api` was only failing because Redis refused writes on
`stop-writes-on-bgsave-error` after its RDB save hit the full disk. It recovers once
Redis has a working volume.

## Phase 1a: hell-gate-bridge publishes to a keyspace nothing reads

**Not caused by the disk incident.** Found while verifying Phase 1. Independent of
Phases 2-4 and can be done in any order.

**Done 2026-09-07.** Both `INGEST_VEHICLE_ID` values now carry the surrogate
`Tracker.id`. Within one poll the amtrak feed went to `has_vehicles: true` /
`has_trip_updates: true`, `vehicle_positions.pb` from 15 bytes to 3375, the alert
sync from `8 scraped -> 0 synced` to `8 scraped -> 8 synced`, and both Gatus feed
checks from `success=false` to `success=true`. cafe-car was hardened alongside it
(see *Hardening* below) so the same misconfiguration cannot be silent again.

Every feed serves a valid but **empty** protobuf, and `/feeds` reports
`has_vehicles: false` on all six. Ingest looks healthy: hell-gate-bridge logs
`amtrak: 37 vehicles -> 37 positions, 36 trip-updates published`, cafe-car answers
every `POST /ingest/position` and `/ingest/trip-update` with 200, and Redis DB1
holds ~73 live keys.

One path was **not** silent, and was missed on the first pass:
`POST /ingest/alerts` answered **403 Forbidden** every cycle
(`alerts: 8 scraped -> 0 synced`), because `ingest.py` resolves the tracker there
and rejects an id it cannot find. The `has_alerts: true` on the amtrak feed was
stale Postgres rows, not a live sync. Three ingest paths, one cause.

The keys are written under the wrong name. `gtfs/hell-gate-bridge.yaml` sets:

| Deployment | `INGEST_VEHICLE_ID` | What it actually is |
|---|---|---|
| `hell-gate-bridge-amtrak` (line 44) | `amtrak-live` | `tracker.device_key` |
| `hell-gate-bridge-buswhere` (line 77) | `columbia-county` | `tracker.device_key` |

cafe-car scans `vehicle:{Tracker.id}:*` (`src/cafe_car/routers/gtfs_rt.py:53,172`),
and `PositionIngest.tracker_id` is documented as "the tracker's surrogate id
(`Tracker.id`), not its `device_key`". So the pollers write
`vehicle:amtrak-live:...` while the serializer looks for
`vehicle:fbacbb1b6c1cfc37a37342f5db7b1f14:...` and finds nothing.

This is exactly the silent failure the file's own comment at line 9 warns about. It
has been in place since `3f1cc67` (2026-07-31), about five weeks, with no error
anywhere in the path.

### Fix

Read the surrogate ids from the live database rather than trusting the ones below;
they are recorded here as of 2026-09-07 and a re-provision changes them:

```bash
ssh kcfam 'export KUBECONFIG=/etc/rancher/k3s/k3s.yaml; \
  kubectl -n gtfs exec postgres-1 -- \
    psql -U postgres -d rt_api -c "select nickname, device_key, id from tracker;"'
```

| `device_key` | `Tracker.id` |
|---|---|
| `amtrak-live` | `fbacbb1b6c1cfc37a37342f5db7b1f14` |
| `columbia-county` | `eac865d0127347eccc850b894baa6048` |

Set both `INGEST_VEHICLE_ID` values in `gtfs/hell-gate-bridge.yaml` to the matching
`Tracker.id`, then render and commit as usual:

```bash
PATH="$HOME/.local/bin:$PATH" SOPS_AGE_KEY_FILE=$PWD/age.key \
  kustomize build --enable-alpha-plugins --enable-exec gtfs
```

Note the old `vehicle:amtrak-live:*` keys carry a 60s TTL, so they age out on their
own; no Redis cleanup is needed.

### Hardening

Pinning the right ids fixes today's outage but not the class of bug, so cafe-car
(`src/cafe_car/routers/ingest.py`) was changed too:

- A `_resolve_tracker` helper looks a tracker up by `Tracker.id` and falls back to
  `device_key`, the same order `provisioning.upsert_tracker` already used. A
  producer configured with the readable `device_key` now works instead of writing
  to a namespace nobody reads.
- `/ingest/position` resolves before building the record and keys Redis off
  `tracker.id`, never the value the producer sent.
- A `tracker_id` that resolves to nothing is still stored and not published, but is
  now **logged as a warning**. That single line is what was missing for five weeks:
  every POST answered 200 while the feed served an empty protobuf.
- `/ingest/alerts` resolves the same way, so a `device_key` no longer 403s.

should be days, not months.

### 2.1 Stage the tarball off /srv

Add to all three `docker_container` backup resources:

```hcl
volumes {
  host_path      = "/mnt/backups/tmp"
  container_path = "/tmp"
}
```

`/mnt/backups` is `/dev/sdc1`, a separate 916G disk. A staging file there can no
longer touch Longhorn or the k3s stack.

Create the directory first; it did not exist, and `/mnt/backups` is root-owned with
no passwordless sudo on `kcfam`:

```bash
ssh kcfam 'docker run --rm -v /mnt/backups:/b alpine mkdir -p /b/tmp'
```

Side effect worth knowing: with `/tmp` bind-mounted, a leaked staging file now
**survives a container restart**. That is a net improvement, since the file becomes
visible to `du` and deletable instead of being an invisible open inode, but the
Phase 0 remedy (restart the container) no longer reclaims it. Nothing cleans
`/mnt/backups/tmp` automatically, so the `BackupStale`/disk alerts in Phase 4 are
what keeps this honest.

### 2.2 Exclude the live logs

`nextcloud.log` is 133M and written continuously, which is what threw
`archive/tar: write too long`. Append `|\.log$` to `BACKUP_EXCLUDE_REGEXP` on
`backup-daily` and `backup-weekly`:

```hcl
"BACKUP_EXCLUDE_REGEXP=^/backup/tmp/|\\.tmp$|\\.log$|/backup/immich_upload/backups/",
```

### 2.3 Shrink the daily

This is the part that makes the interim actually fit, and it is not optional.

`/mnt/backups` is 916G. The peak during a daily run is
`staging + N_old * 188G + new + weekly 187G + monthly 8G`. offen's retention is
day-granular with no keep-N option, so it can leave two dailies behind, which puts
the peak at about 947G. That still overflows, just onto a different disk.

So for the interim, remove the `docker_volume.nextcloud` mount from `backup-daily`,
leaving `immich_upload` and `immich_postgres` (~16.5G), and let `backup-weekly` carry
the full nextcloud set.

Resulting peaks: daily ~259G, weekly ~603G. Both comfortable.


Only the three backup containers should be replaced. After the next 02:00 run:

```bash

ssh kcfam 'ls -lh /mnt/backups/tmp /mnt/backups/daily'
```

The log should end in `Removed tar file` with no error, and the staging file should

Deviations from what is written below, all deliberate:

- `backup-daily`'s `BACKUP_FILENAME` is now `homeserver-db-%Y%m%d-%H%M%S.tar.gz`.
  It shares `/mnt/backups/daily` with the old 188G `homeserver-backup-*` tarballs and

- `BACKUP_EXCLUDE_REGEXP` on that container drops the `\.log$` and

- A `textfile_collector` docker volume carries the metric from restic to

  volume avoids another root-owned host directory like `/mnt/backups/tmp`.


A 188G gzip of mostly-unchanged photos, taken daily, is the wrong shape for this
data. restic dedups, needs no staging file, and cannot fill a disk the way a

**Correction to 4.2/4.3 below: there is no `docker_image.alertmanager`.** The plan
had Alertmanager follow the `prometheus/` pattern (local Dockerfile, `dir_sha1`
trigger) while also taking the chat id from a Terraform variable. Those two are
incompatible: a `docker_image` build context is static files on disk and cannot see
Terraform variables, so the chat id could never reach a baked config. Alertmanager
therefore runs the upstream `prom/alertmanager` image, and both its config (rendered
from `alertmanager.yml.tftpl` with `templatefile()`) and its token arrive as `upload`
blocks. This is strictly better anyway: the token never enters an image layer, and a
config change no longer needs an image rebuild. `tf/images.tf` is unchanged.

Three rules were added beyond the four planned. `CadvisorDockerFactoryDown` and
`ContainerMissing` came out of Phase 0b: the first fires when no `container_*` series
carries a `name` label, which is the state cadvisor sat in unnoticed; the second
fires when a container on an explicit always-on list stops being seen, which is what
`immich_postgres` did for five hours. `ContainerMissing` is guarded by
`and on () (count(container_last_seen{name!=""}) > 0)` so a nameless cadvisor pages
once for itself instead of once per listed container. The expression was checked
against the live Prometheus, not just `promtool`: with cadvisor healthy it returns
only the containers that genuinely do not exist.

The third is `BackupMetricMissing`, an
`absent()` guard. `BackupStale` subtracts from
`homeserver_backup_last_success_timestamp_seconds`, so if that metric never appears,
because the textfile collector is miswired or restic has never completed a run, the
staleness rule silently cannot fire. That is the same class of failure as the Gatus
gap in Phase 1a, so it is worth the extra rule.

`home-docker/CLAUDE.md` should get a note about the `upload` pattern, as planned, but
only once it has actually run. It has not.


`prometheus/prometheus.yml` already has `rule_files:` stubbed out. Configs are baked
into images here because the Docker host is remote, and `docker_image.prometheus`

## Recommendation, not planned work

`/srv` is shared by Docker (233G) and Longhorn (2.9G) with no isolation. That shared
fate is why a Nextcloud backup took down the transit stack. Giving Longhorn its own
partition, or moving Docker's data root off `sda5`, is the durable fix.

Tradeoffs: it needs a repartition or a new disk, downtime for both stacks, and a
Longhorn disk migration (add the new disk, evict the old one, remove it). Longhorn's
`storageMinimalAvailablePercentage` does not help here, since it only reserves space
against Longhorn's own scheduling and cannot stop Docker from filling the filesystem.

This was not part of what was agreed. Raise it separately.
